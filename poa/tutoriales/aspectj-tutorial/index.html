// El Problema

¿Por qué necesitamos AOP?

La Programación Orientada a Objetos es excelente para modelar el dominio, pero falla cuando hay comportamientos que "cortan" transversalmente todas las clases.

Problema Código repetido en OOP

ServicioA.java / ServicioB.java / ... 
// Cada clase repite el mismo boilerplate:
public void procesarPedido(Pedido p) {
    log.info("Inicio procesarPedido");   // logging
    checkAuth(usuario);                   // seguridad
    long t = System.currentTimeMillis(); // timing

    // lógica de negocio
    pedidoRepo.save(p);

    long ms = System.currentTimeMillis() - t;
    log.info("Fin: " + ms + "ms");       // logging
}
// → 50 clases × este código = pesadilla

Solución Separación con AOP

LoggingAspect.aj 
// Se define UNA vez, aplica en toda la app:
public aspect LoggingAspect {
    pointcut serviceMethods() :
        execution(* com.app.service.*.*(..));

    before() : serviceMethods() {
        System.out.println("Inicio: "
            + thisJoinPoint.getSignature());
    }

    after() : serviceMethods() {
        System.out.println("Fin del método");
    }
}
// → El servicio queda completamente limpio

Módulo Pedidos

Con AOP, los concerns en azul, rojo y verde se definen una sola vez en un Aspecto — no en cada módulo.

// Compatibilidad

AspectJ es compatible con Java

AspectJ es una extensión compatible de Java para facilitar el uso de aspectos por parte de los programadores. Por compatible se entiende tres dimensiones fundamentales:

Compatibilidad Base

Todos los programas válidos de Java deben ser programas válidos de AspectJ. Cualquier código Java existente funciona sin cambios dentro de un proyecto AspectJ.

Compatibilidad de Plataforma

Todos los programas válidos de AspectJ deben correr sobre la máquina virtual estándar de Java (JVM). No se requiere una JVM especializada o modificada.

Compatibilidad de Programación

La programación en AspectJ debe ser una extensión natural de la programación en Java. Esta meta fue una de las guías más importantes a la hora de tomar decisiones sobre el lenguaje.

AspectJ es estáticamente tipado y usa el sistema de tipos estático de Java. Fue creado en el PARC (Palo Alto Research Center) por el equipo Xerox PARC, liderado por Gregor Kiczales, y se ha convertido en el estándar de facto de la Programación Orientada a Aspectos en el ecosistema Java.

Conceptos Clave

Los 6 pilares que necesitas entender para dominar AspectJ y AOP.

🧩

Aspect

Módulo que encapsula un cross-cutting concern. Equivale a una clase en OOP, pero para comportamiento transversal.

public aspect LogAspect { }
📍

Join Point

Punto específico en la ejecución del programa donde puede actuar un aspecto: llamada a método, constructor, acceso a campo...

method call / execution
⚡

Advice

El código que se ejecuta en el Join Point seleccionado. Puede ser before, after, around, afterReturning o afterThrowing.

before() : pointcut() { }
🔗

Weaving

Proceso de combinar los aspectos con el código base. Puede ocurrir en tiempo de compilación, carga o ejecución.

compile-time / load-time
🧱

Inter-Type Declaration

Entidad estática. Agrega métodos, atributos o constructores a clases existentes desde un aspecto, en tiempo de compilación.

public String Clase.metodo()
🎯

Pointcut

Expresión que selecciona qué Join Points nos interesan. Define dónde se aplicará el advice.

execution(* Service.*(..))
// Aspect

Aspect — Concepto y Declaración

La unidad principal de modularización en AOP. Encapsula un cross-cutting concern y se declara con modificadores únicos que no existen en las clases Java.

En OOP — código disperso

ServicioA.java
package com.app.service;

public class ServicioA {
    public void procesar() {
        log.info("Inicio procesar"); // logging
        checkAuth();                  // seguridad
        // lógica de negocio...
        log.info("Fin procesar");    // logging
    }

    public void guardar() {
        log.info("Inicio guardar");  // logging
        checkAuth();                  // seguridad
        // lógica de negocio...
        log.info("Fin guardar");     // logging
    }
}
// El mismo patrón de logging y seguridad
// se repite en ServicioB, ServicioC... etc.

Con AOP — código centralizado

LoggingAspect.aj
// Aplica a TODOS los métodos de com.app.service.*
// ServicioA, ServicioB, ServicioC... sin tocarlos
public aspect LoggingAspect {
    pointcut servicios() :
        execution(* com.app.service.*.*(..));

    before() : servicios() {
        System.out.println("Inicio: "
            + thisJoinPoint.getSignature());
    }

    after() : servicios() {
        System.out.println("Fin del método");
    }
}
// Llamando servicioA.procesar():
// Inicio: void com.app.service.ServicioA.procesar()
// Fin del método

Sintaxis de declaración

[ privileged ] aspect Id
    [ extends Type ]
    [ implements TypeList ]
    [ Per Clause ]
{
    Body
}
Regla clave: Un aspecto no se instancia con new. El runtime de AspectJ gestiona su ciclo de vida. Por defecto existe una sola instancia por JVM (singleton).

Un modificador especial que le da al aspecto privilegios de acceso: puede leer y modificar métodos y atributos private de clases y aspectos externos sin necesitar getters/setters.

Útil cuando el aspecto necesita inspeccionar estado interno de una clase sin forzar cambios en su API. En el ejemplo, balance es private en Account — sin privileged el aspecto no podría acceder a él.

Account.java
public class Account {
    private double balance; // campo privado

    public Account(double initialBalance) {
        this.balance = initialBalance;
    }

    public void deposit(double amount) {
        this.balance += amount;
    }

    public void withdraw(double amount) {
        if (amount > this.balance)
            throw new IllegalStateException(
                "Fondos insuficientes");
        this.balance -= amount;
    }
    // No hay getBalance() — campo completamente privado
}
PrivilegedAspect.aj
// Sin 'privileged' esto fallaría en compilación:
// "balance has private access in Account"
privileged aspect PrivilegedAspect {

    before() : execution(* Account.deposit(..)) {
        Account a =
            (Account) thisJoinPoint.getTarget();
        // Acceso directo al campo private
        System.out.println(
            "Balance antes del depósito: "
            + a.balance);
    }

    after() : execution(* Account.deposit(..)) {
        Account a =
            (Account) thisJoinPoint.getTarget();
        System.out.println(
            "Balance después del depósito: "
            + a.balance);
    }
}
// Llamando: account.deposit(500.0)
// con balance inicial = 1000.0
//
// [before]  Balance antes del depósito:  1000.0
// → deposit() ejecuta: balance += 500.0
// [after]   Balance después del depósito: 1500.0

Un aspecto puede extender una clase o un aspecto abstracto, e implementar tantas interfaces como se le indiquen. Reglas importantes:

  • Un aspecto, aunque extienda una clase, no puede instanciarse con new.
  • Una clase no puede extender un aspecto.
  • Un aspecto no puede extender un aspecto que no sea abstracto.
AbstractLogging.aj / ConcreteLogging.aj
// Aspecto abstracto base
public abstract aspect AbstractLogging {
    abstract pointcut loggedMethods();

    before() : loggedMethods() {
        System.out.println("Entering: " + thisJoinPoint.getSignature());
    }
}

// Aspecto concreto que extiende el abstracto
public aspect ConcreteLogging extends AbstractLogging {
    pointcut loggedMethods() : execution(* com.app.service.*.*(..));
}

Por defecto, los aspectos son singleton (una sola instancia por JVM). Las Per Clauses permiten controlar cuántas instancias del aspecto existen y bajo qué condiciones:

  • issingleton() — Una instancia global (comportamiento por defecto).
  • perthis(pointcut) — Una instancia por objeto en el que se ejecuta el aspecto.
  • pertarget(pointcut) — Una instancia por objeto destino del join point.
  • percflow(pointcut) — Una instancia por flujo de control que alcanza el pointcut.
PerInstanceAspect.aj
// Una instancia del aspecto por cada objeto Account
public aspect AccountAudit perthis(execution(* Account.*(..))) {
    private int operationCount = 0;

    pointcut accountOps() : execution(* Account.*(..));

    after() : accountOps() {
        operationCount++;
        System.out.println("Operaciones en esta cuenta: " + operationCount);
    }
}
// Nota: no se recomienda mezclar varios per clauses
// ya que pueden interferir con flujos de otros aspectos.
// Join Point

Join Point — El Punto de Intercepción

Un Join Point es cualquier punto identificable en la ejecución del programa donde un aspecto puede actuar.

method execution

Ejecución del cuerpo de un método. El más común.

execution(* Clase.*(..))

method call

Llamada a un método desde otro punto del código.

call(* Clase.*(..))

constructor execution

Ejecución del constructor de una clase.

execution(Clase.new(..))

field access

Lectura o escritura de un campo de una clase.

get(* Clase.*) / set(* Clase.*)
PedidoService.java
package com.app.service;

public class PedidoService {

    public void procesarPedido(Pedido pedido) {
        // lógica de negocio
        System.out.println(
            "Procesando pedido: " + pedido.getId());
    }

    public Pedido buscarPedido(int id) {
        return new Pedido(id, "Producto X");
    }
}
JoinPointInfo.aj
public aspect JoinPointInfo {

    before() : execution(* com.app.service.*.*(..)) {
        // Tipo de join point: method-execution, call, etc.
        System.out.println("Tipo:   "
            + thisJoinPoint.getKind());

        // Nombre del método interceptado
        System.out.println("Método: "
            + thisJoinPoint.getSignature().getName());

        // Clase donde se ejecuta el método
        System.out.println("Clase:  "
            + thisJoinPoint.getTarget()
                           .getClass()
                           .getSimpleName());

        // Argumentos recibidos por el método
        System.out.println("Args:   "
            + Arrays.toString(thisJoinPoint.getArgs()));
    }
}
// Llamando procesarPedido(pedido) → imprime:
// Tipo:   method-execution
// Método: procesarPedido
// Clase:  PedidoService
// Args:   [Pedido@3f99bd52]
// Advice

Advice — El Comportamiento

El código que se ejecuta cuando un aspecto actúa en un Join Point. Define qué hacer y cuándo hacerlo.

before()

Se ejecuta antes del método. Ideal para validación, logging de entrada o seguridad. No puede detener la ejecución (salvo excepción).

after()

Se ejecuta siempre después, en éxito o error. Equivalente al bloque finally.

after returning()

Se ejecuta solo si el método retorna normalmente. Puede capturar el valor de retorno.

after throwing()

Se ejecuta solo si el método lanza una excepción. Puede capturar la excepción lanzada.

around()

Envuelve el método completamente. Control total — puede modificar args, cambiar el resultado o evitar la ejecución. Requiere proceed().

around() { inicio...
→
before()
→
método()
→
after()
→
...fin }
PagoService.java
public class PagoService {

    public String procesarPago(double monto) {
        if (monto <= 0)
            throw new IllegalArgumentException(
                "Monto inválido: " + monto);

        System.out.println(
            "Procesando pago de $" + monto);
        return "TXN-" + System.currentTimeMillis();
    }
}
AllAdvicesAspect.aj
public aspect AllAdvicesAspect {

    pointcut pago() :
        execution(* PagoService.procesarPago(..));

    // 1. Se ejecuta SIEMPRE antes del método
    before() : pago() {
        System.out.println("[before] validando pago...");
    }

    // 2. Se ejecuta SIEMPRE después (éxito o error)
    after() : pago() {
        System.out.println("[after] operación finalizada");
    }

    // 3. Solo si el método retornó SIN excepción
    after() returning(String txn) : pago() {
        System.out.println("[returning] TXN generada: " + txn);
    }

    // 4. Solo si el método LANZÓ excepción
    after() throwing(Exception ex) : pago() {
        System.out.println("[throwing] error: " + ex.getMessage());
    }

    // 5. Envuelve el método — control total
    Object around() : pago() {
        long t = System.currentTimeMillis();
        System.out.println("[around] inicio");
        Object result = proceed(); // ejecuta procesarPago()
        System.out.println("[around] fin en "
            + (System.currentTimeMillis() - t) + "ms");
        return result;
    }
}
// Llamando procesarPago(150.0):
//   [around] inicio
//   [before] validando pago...
//   Procesando pago de $150.0
//   [after]     operación finalizada
//   [returning] TXN generada: TXN-1716300000000
//   [around] fin en 3ms
//
// Llamando procesarPago(-5):
//   [around] inicio
//   [before] validando pago...
//   [after]    operación finalizada
//   [throwing] error: Monto inválido: -5.0
// Pointcuts

Pointcut — Patrones y Selección

Seleccionan dónde y cuándo se ejecutará el código de un aspecto (conjuntos de join points).

Sintaxis básica

Un pointcut identifica métodos, accesos o llamadas en Java mediante una expresión de patrón clara.

syntax
pointcut NombreDelPointcut() :
    ModificadorDeAcceso TipoDeRetorno ClaseMetodo.metodo(parametros);
  • NombreDelPointcut: identificador del pointcut.
  • ModificadorDeAcceso: public, private, protected o package.
  • TipoDeRetorno: tipo devuelto o * para cualquier tipo.
  • ClaseMetodo: clase que define el método.
  • Metodo: nombre del método a interceptar.
  • Parametros: lista de parámetros del método.

Tipos comunes de selección

Los pointcuts pueden elegir ejecución, llamada, acceso a campos y combinaciones lógicas.

pointcuts
// execution: selecciona el cuerpo del método
pointcut todosLosEnterosPublicos() :
    execution(public int *(..));

pointcut servicioFacturacion() :
    execution(* com.finanzas.services.FacturacionService.procesarPago(..));

// call: selecciona el lugar de invocación
pointcut cuandoLlamenADepositar() :
    call(* com.finanzas.Cuenta.depositar(..));

// get / set: selecciona acceso a campos
pointcut cambioDeBalance() :
    set(double com.finanzas.Cuenta.balance);

// Operadores lógicos
pointcut serviciosModificadores() :
    execution(* com.finanzas.services.*.*(..))
    && !execution(* com.finanzas.services.*.get*(..));

Pointcut — patrones y comodines

ejemplos
// * → exactamente un token  |  .. → cero o más tokens

// Todos los métodos de cualquier clase Service
pointcut serviceMethods() :
    execution(* com.app.service.*.*(..));

// Métodos con exactamente dos parámetros
pointcut twoParams() :
    call(void MiClase.metodo(*, *));

// Combinando con operadores lógicos
pointcut serviceWithString() :
    execution(* com.app.service.*.*(..))
    && execution(* *.*(.., String, ..));

// Capturar argumentos del método
pointcut lending(Member m, Book b) :
    execution(void Library.lendBook(Member, Book))
    && args(m, b);

Contexto y diferencias

Los pointcuts pueden exponer objetos y valores de argumentos para que el advice los reutilice.

call: se activa en el sitio donde se hace la llamada. Ideal para interceptar interfaces y llamadas externas.
execution: se activa cuando el cuerpo del método se ejecuta. Ideal para trazas y cuando importa la implementación real.

// Weaving

Weaving — El Ensamblaje

El proceso mediante el cual los aspectos se combinan con el código base. Es lo que hace que el advice realmente se ejecute en los join points seleccionados.

Compile-time Weaving

El compilador ajc teje los aspectos directamente en el bytecode durante la compilación. Es el más eficiente — sin overhead en ejecución.

terminal
// ajc compila y teje al mismo tiempo
ajc -sourceroots src/ -outjar app.jar

// Con Maven — ajc reemplaza a javac:
mvn clean compile

Post-compile Weaving

Teje aspectos sobre archivos .class ya compilados o JARs de terceros. Útil cuando no tienes el código fuente de la librería.

terminal
// Teje sobre un JAR externo
ajc -inpath libreria.jar
    -aspectpath mis-aspectos.jar
    -outjar resultado.jar

Load-time Weaving (LTW)

Los aspectos se tejen cuando la JVM carga las clases. No requiere recompilar — se configura con un agente Java.

terminal / aop.xml
// Iniciar JVM con el agente de AspectJ:
java -javaagent:aspectjweaver.jar -jar app.jar

// aop.xml — declara qué aspectos aplicar:
// <aspectj>
//   <aspects>
//     <aspect name="com.app.LoggingAspect"/>
//   </aspects>
// </aspectj>
Tipo Cuándo ocurre Rendimiento Flexibilidad
Compile-time Compilación ✓ Máximo ~ Media
Post-compile Post-compilación ✓ Alto ✓ Alta
Load-time Carga de clases ~ Medio ✓ Máxima
// Entidad Estática

Inter-Type Declarations

La única entidad estática de AspectJ. Permite modificar la estructura de clases existentes en tiempo de compilación — sin tocar su código fuente.

A diferencia de Pointcuts y Advices que actúan en tiempo de ejecución, las Inter-Type Declarations actúan en tiempo de compilación: agregan métodos, atributos o constructores directamente a la estructura de clases externas, como si siempre hubieran estado ahí.

⚡ Entidades Dinámicas

Actúan en tiempo de ejecución. Interceptan el flujo del programa.

  • Join Point — dónde puede ocurrir algo
  • Pointcut — qué join points seleccionar
  • Advice — qué ejecutar en esos puntos

🧱 Entidad Estática

Actúa en tiempo de compilación. Modifica la estructura del programa.

  • Inter-Type Declaration — agrega miembros a clases externas
  • Afecta la firma estática de la clase
  • El compilador la trata como parte de la clase original

¿Qué se puede declarar con ITD?

Métodos

Agrega métodos nuevos a una clase existente. La clase los hereda como si fueran propios.

public String Clase.nuevoMetodo()

Atributos

Agrega campos (variables de instancia) a una clase. Cada instancia de la clase tendrá ese campo.

private String Clase.nuevoAtributo

Constructores

Agrega nuevos constructores a una clase, permitiendo nuevas formas de instanciarla.

public Clase.new(String param)

declare parents

Hace que una clase extienda otra clase o implemente interfaces, sin tocar su código fuente.

declare parents: Clase implements IFaz

Desde un aspecto se puede "inyectar" un método o atributo en una clase existente. La clase User no declara auditId ni sus getters — el compilador los agrega en el weaving.

User.java
public class User {
    private String name;

    public User(String name) {
        this.name = name;
    }

    public String getName() {
        return name;
    }
    // No tiene auditId, getAuditInfo()
    // ni setAuditId() — los agrega el aspecto
}
AuditAspect.aj
public aspect AuditAspect {

    // ITD: agrega atributo privado a User
    private String User.auditId;

    // ITD: agrega método público a User
    public String User.getAuditInfo() {
        return "User[" + this.getName()
            + "] auditId=" + this.auditId;
    }

    // ITD: agrega setter a User
    public void User.setAuditId(String id) {
        this.auditId = id;
    }
}
Main.java
public class Main {
    public static void main(String[] args) {

        User u = new User("Felipe");

        // Métodos inyectados por AuditAspect — disponibles en User
        u.setAuditId("AUD-001");
        System.out.println(u.getAuditInfo());
        // → User[Felipe] auditId=AUD-001

        User u2 = new User("Carlos");
        u2.setAuditId("AUD-002");
        System.out.println(u2.getAuditInfo());
        // → User[Carlos] auditId=AUD-002
    }
}

declare parents es una forma especial de ITD que modifica la jerarquía de tipos de una clase — sin editar su código fuente. Muy útil para retrofitting de interfaces en clases legacy.

SerializableAspect.aj
import java.io.Serializable;

public aspect SerializableAspect {

    // Hace que todas las clases del paquete
    // model implementen Serializable
    declare parents: com.app.model.* implements Serializable;

    // También puede hacer que una clase extienda otra:
    // declare parents: ConcreteClass extends AbstractBase;
}

// Ahora cualquier instancia de com.app.model.*
// puede usarse donde se requiera Serializable
// sin haber modificado ninguna clase del paquete.

Un aspecto puede agregar un constructor adicional a una clase existente, permitiendo nuevas formas de instanciarla sin modificar su código.

Product.java
public class Product {
    private String nombre;
    private double precio;

    // Constructor original — solo nombre y precio
    public Product(String nombre, double precio) {
        this.nombre = nombre;
        this.precio = precio;
    }

    public String getNombre() { return nombre; }
    public double getPrecio() { return precio; }
    // No tiene constructor con 'categoria'
}
FactoryAspect.aj
public aspect FactoryAspect {

    // ITD: agrega un constructor alternativo a Product
    public Product.new(String nombre,
                       double precio,
                       String categoria) {
        // llama al constructor original de Product
        this(nombre, precio);
        System.out.println(
            "Producto creado en categoría: "
            + categoria);
    }
}

// Main.java — el nuevo constructor ya está disponible:
// Product p1 = new Product("Mouse", 25.0);
// → constructor original, sin categoría
//
// Product p2 = new Product("Laptop", 2500.0, "Electrónica");
// → Producto creado en categoría: Electrónica
Diferencia clave con Advice: Un advice intercepta la ejecución en tiempo de ejecución y puede evitar o modificar el comportamiento. Una ITD extiende la estructura en tiempo de compilación — el miembro agregado existe permanentemente en la clase compilada, como si siempre hubiera sido parte de ella.

Compiladores para AspectJ

AspectJ requiere un compilador especializado que entienda la sintaxis de aspectos y realice el weaving en tiempo de compilación.

ajc

El compilador oficial de AspectJ, parte de las herramientas soportadas por el proyecto Eclipse. Es el compilador de referencia y el más usado en producción.

Soporta compile-time weaving y load-time weaving. Se integra con Maven y Gradle mediante el aspectj-maven-plugin.

abc

El AspectBench Compiler, un compilador extensible y optimizador producido en aspectbench.org. Diseñado para investigación y como plataforma extensible para nuevas características AOP.

Genera bytecode más optimizado en algunos escenarios y permite agregar extensiones al lenguaje de aspectos.

aspectbench.org
Característica ajc (AspectJ Compiler) abc (AspectBench Compiler)
Origen e Infraestructura Desarrollado por Xerox PARC y mantenido por Eclipse. Está basado directamente en el compilador de Eclipse (ecj). Desarrollado por un consorcio académico (Oxford, McGill, Aarhus). Se apoya en las herramientas Polyglot y Soot.
Enfoque Productividad en entornos industriales, velocidad de compilación rápida y compatibilidad con IDEs. Investigación académica, experimentación con el lenguaje y optimización estricta del rendimiento.
Representación interna Genera un Árbol de Sintaxis Abstracta (AST) unificado a partir de los archivos .java y .aj. Traduce el AST a Jimple, una representación intermedia de código de 3 direcciones tipada y simplificada.
Weaving Modifica el bytecode directamente inyectando ganchos (hooks) o llamadas directas en las líneas del código objetivo. Realiza el tejido de aspectos de forma optimizada sobre la representación Jimple, aprovechando su flujo de control limpio.
Capacidad de Optimización Para pointcuts dinámicos (como cflow), introduce comprobaciones redundantes en tiempo de ejecución en cada llamada. Realiza análisis de flujo estático para evaluar qué comprobaciones son innecesarias y eliminarlas en la compilación.
Salida Produce archivos .class estándar con instrucciones duplicadas o redirigidas que la JVM lee de forma normal. El framework Soot vuelve a empaquetar y transformar el código Jimple ya optimizado en bytecode de Java.
En la práctica: ajc es el compilador estándar para proyectos reales. Al ejecutar mvn compile con el plugin configurado, ajc reemplaza al compilador de Java y realiza el weaving automáticamente.

🏧 Cajero Automático — before() y after()

El aspecto registra el inicio y fin de cada operación usando before() y after(). thisJoinPoint permite acceder al nombre del método y sus argumentos en tiempo de ejecución, sin hardcodear nada en el aspecto.

Lógica de negocio pura — sin una sola línea de logging. Todo el registro lo maneja el aspecto de forma transparente.
CajeroAutomatico.java
public class CajeroAutomatico {
    private double saldo;

    public CajeroAutomatico(double saldoInicial) { this.saldo = saldoInicial; }

    public double consultarSaldo() { return saldo; }

    public void depositar(double monto) {
        saldo += monto;
        System.out.println("Depósito realizado: +" + monto);
    }

    public void retirar(double monto) {
        if (monto > saldo) throw new IllegalStateException("Fondos insuficientes");
        saldo -= monto;
        System.out.println("Retiro realizado: -" + monto);
    }

    public static void main(String[] args) {
        CajeroAutomatico cajero = new CajeroAutomatico(1000.0);
        cajero.depositar(500.0);
        cajero.retirar(200.0);
        System.out.println("Saldo final: " + cajero.consultarSaldo());
    }
}
before() se ejecuta antes de cada operación; after() siempre al final (como finally). thisJoinPoint da acceso al contexto de ejecución.
AuditoriaAspect.aj
import java.util.Arrays;

public aspect AuditoriaAspect {

    // Intercepta todos los métodos del cajero excepto main()
    pointcut operaciones() :
        execution(* CajeroAutomatico.*(..))
        && !execution(* CajeroAutomatico.main(..));

    before() : operaciones() {
        System.out.println("[ANTES] " + thisJoinPoint.getSignature().getName()
            + " | args: " + Arrays.toString(thisJoinPoint.getArgs()));
    }

    after() : operaciones() {
        System.out.println("[DESPUÉS] " + thisJoinPoint.getSignature().getName()
            + " completado\n");
    }
}
// [ANTES] depositar | args: [500.0]
// Depósito realizado: +500.0
// [DESPUÉS] depositar completado

🍽️ Restaurante — comodines * en pointcuts

El comodín * en el nombre del método coincide con cualquier secuencia de caracteres. preparar* selecciona todos los métodos que empiezan con "preparar" — sin importar cuántos sean ni qué nombre tengan después.

Tres métodos de preparación y uno de cobro. Los comodines los distinguen automáticamente por nombre.
Restaurante.java
public class Restaurante {

    public void prepararEntrada(String plato) {
        System.out.println("  Preparando entrada: " + plato);
    }

    public void prepararPrincipal(String plato) {
        System.out.println("  Preparando principal: " + plato);
    }

    public void prepararPostre(String plato) {
        System.out.println("  Preparando postre: " + plato);
    }

    public double cobrar(int numMesa) {
        System.out.println("  Cobrando mesa " + numMesa);
        return 45.50;
    }

    public static void main(String[] args) {
        Restaurante r = new Restaurante();
        r.prepararEntrada("Ensalada César");
        r.prepararPrincipal("Pasta Carbonara");
        r.prepararPostre("Tiramisú");
        r.cobrar(5);
    }
}
preparar* captura los 3 métodos de cocina. *(..) captura todos. La exclusión !cocina() aísla solo cobrar().
OrdenAspect.aj
public aspect OrdenAspect {

    // preparar* → prepararEntrada, prepararPrincipal, prepararPostre
    // (..)       → cualquier número de parámetros
    pointcut cocina() : call(void Restaurante.preparar*(..));

    // *(..) : cualquier nombre, cualquier parámetro
    pointcut cualquiera() : call(* Restaurante.*(..));

    before() : cocina() {
        System.out.println("[COCINA] Orden recibida: "
            + thisJoinPoint.getSignature().getName());
    }

    // cualquiera() && !cocina() captura solo cobrar()
    after() : cualquiera() && !cocina() {
        System.out.println("[CAJA] Operación finalizada: "
            + thisJoinPoint.getSignature().getName());
    }
}
// prepararEntrada() → dispara cocina
// cobrar()          → dispara caja  (no cocina)

🚗 Tráfico — call() vs execution()

call() actúa en el sitio de la llamada (el caller). execution() actúa dentro del cuerpo del método. La diferencia es crítica con herencia: el cuerpo de arrancar() vive en Vehiculo, aunque la llamada sea a través de Moto.

Define arrancar(). El cuerpo del método vive aquí — execution() se dispara en Vehiculo, incluso si la llamada vino de Moto.
Vehiculo.java
public class Vehiculo {

    public void arrancar() {
        System.out.println("  Motor encendido");
    }

    public void frenar() {
        System.out.println("  Frenos aplicados");
    }

    public static void main(String[] args) {
        Moto moto = new Moto();

        System.out.println("=== moto.arrancar() ===");
        moto.arrancar();  // → CALL (en main) + cuerpo + EXEC (en Vehiculo)

        System.out.println("\n=== moto.frenar() ===");
        moto.frenar();    // → EXEC(frenar) pero NO call(Moto.arrancar)
    }
}
Hereda arrancar() sin sobreescribirla. El bytecode del método sigue en Vehiculo.
Moto.java
public class Moto extends Vehiculo {
    // Hereda arrancar() y frenar() sin sobreescribirlos.
    // El cuerpo de ambos métodos sigue viviendo en Vehiculo.
}
call(Moto.arrancar) actúa en main antes de entrar. execution(Vehiculo.arrancar) actúa dentro del cuerpo en Vehiculo.
SensorTrafico.aj
public aspect SensorTrafico {

    // call: se activa en el LUGAR DE LA LLAMADA (Vehiculo.main)
    before() : call(* Moto.arrancar()) {
        System.out.println("  [CALL]  llamada a Moto.arrancar() detectada");
    }

    // execution: se activa DENTRO DEL CUERPO del método (Vehiculo)
    after() : execution(* Vehiculo.arrancar()) {
        System.out.println("  [EXEC]  Vehiculo.arrancar() terminó");
    }
}
// Salida para moto.arrancar():
//   [CALL]  llamada a Moto.arrancar() detectada
//   Motor encendido
//   [EXEC]  Vehiculo.arrancar() terminó
//
// Salida para moto.frenar():
//   Frenos aplicados        ← execution(Vehiculo.frenar) sí dispara
//                           ← call(Moto.arrancar) NO dispara (es frenar)

📋 Agenda — Inter-Type Declarations (ITD)

Un aspecto puede inyectar campos y métodos en clases existentes sin tocar su código fuente. PrioridadAspect añade el campo prioridad y los métodos setPrioridad() / getPrioridad() a Tarea — completamente transparente para la clase.

Clase simple con descripción y ejecutar(). No declara ningún campo de prioridad — lo inyecta el aspecto.
Tarea.java
public class Tarea {
    private String descripcion;

    public Tarea(String descripcion) { this.descripcion = descripcion; }

    public void ejecutar() {
        System.out.println("  Ejecutando: " + descripcion);
    }

    public String getDescripcion() { return descripcion; }
}
Los ITDs inyectan el campo int prioridad y dos métodos en Tarea. El before() lee ese campo para mostrarlo antes de ejecutar.
PrioridadAspect.aj
public aspect PrioridadAspect {

    // ITD: inyecta campo en Tarea (5 = prioridad normal por defecto)
    int Tarea.prioridad = 5;

    // ITD: inyecta métodos en Tarea
    public void Tarea.setPrioridad(int p) { this.prioridad = p; }
    public int  Tarea.getPrioridad()      { return this.prioridad; }

    // Advice que usa el campo inyectado
    before() : execution(void Tarea.ejecutar()) {
        Tarea t = (Tarea) thisJoinPoint.getTarget();
        System.out.printf("  [ITD] %-25s  prioridad: %d%n",
            t.getDescripcion(), t.prioridad);
    }
}
// Tarea.java no declara 'prioridad', 'setPrioridad' ni 'getPrioridad'
// ajc los inyecta en el bytecode vía ITD — transparente para la clase
Main llama setPrioridad() y getPrioridad() como si Tarea los declarara — porque gracias al ITD, sí lo hace en bytecode.
Main.java
public class Main {
    public static void main(String[] args) {
        Tarea t1 = new Tarea("Estudiar AspectJ");
        Tarea t2 = new Tarea("Revisar correos");
        Tarea t3 = new Tarea("Hacer ejercicio");

        // setPrioridad() y getPrioridad() los inyectó PrioridadAspect (ITD)
        t1.setPrioridad(1);   // urgente
        t2.setPrioridad(3);   // media
        // t3 queda en 5 (valor por defecto del campo inyectado)

        System.out.println("t1: " + t1.getPrioridad());  // 1
        System.out.println("t2: " + t2.getPrioridad());  // 3
        System.out.println("t3: " + t3.getPrioridad());  // 5
        System.out.println();

        t1.ejecutar();
        t2.ejecutar();
        t3.ejecutar();
    }
}

🌡️ Termostato — declare parents

declare parents permite que un aspecto haga que una clase implemente una interfaz y proporcione los métodos requeridos, todo sin modificar el código original. Termostato pasa a ser un Reportable de forma completamente transparente.

Clase de dominio simple. No implementa ninguna interfaz en su código fuente — el aspecto lo hace por ella.
Termostato.java
public class Termostato {
    private int temperatura;

    public Termostato(int tempInicial) { this.temperatura = tempInicial; }

    public void ajustar(int nuevaTemp) {
        this.temperatura = nuevaTemp;
        System.out.println("  Temperatura ajustada a: " + nuevaTemp + "°C");
    }

    public int getTemperatura() { return temperatura; }

    public static void main(String[] args) {
        Termostato t = new Termostato(20);
        t.ajustar(28);

        // generarReporte() lo agregó DiagnosticoAspect via declare parents
        t.generarReporte();

        // Termostato es ahora un Reportable — el cast funciona
        Reportable r = (Reportable) t;
        r.generarReporte();
    }
}
Contrato que Termostato no implementa en su código. El aspecto lo implementa por él.
Reportable.java
public interface Reportable {
    void generarReporte();
}
declare parents hace la declaración de implementación. El ITD del método satisface el contrato de la interfaz.
DiagnosticoAspect.aj
public aspect DiagnosticoAspect {

    // Hace que Termostato implemente Reportable sin tocar Termostato.java
    declare parents: Termostato implements Reportable;

    // Proporciona la implementación que la interfaz requiere
    public void Termostato.generarReporte() {
        System.out.println("  [REPORTE] Temperatura: " + this.temperatura + "°C");
        System.out.println("  [REPORTE] Estado: "
            + (temperatura > 25 ? "CALEFACCIÓN ACTIVA" : "NORMAL"));
    }
}
// Después del weaving:
//   (Reportable) termostato  → cast válido
//   termostato.generarReporte() → llama al método del aspecto

📝 Registro de Usuarios — args() + after() throwing

args() vincula los parámetros del método a variables del advice para poder usarlos en la validación. after() throwing es el complemento de after() returning: solo se ejecuta cuando el método lanzó una excepción.

Lógica de negocio sin ninguna validación propia — la delega completamente al aspecto.
RegistroUsuarios.java
public class RegistroUsuarios {

    public void registrar(String nombre, String email, int edad) {
        System.out.println("  Registrado: " + nombre
            + " <" + email + ">  edad: " + edad);
    }

    public void eliminar(String email) {
        if (email == null || email.isEmpty())
            throw new IllegalArgumentException("Email requerido");
        System.out.println("  Eliminado: " + email);
    }

    public static void main(String[] args) {
        RegistroUsuarios reg = new RegistroUsuarios();
        reg.registrar("María", "maria@uni.edu", 22);  // OK
        reg.eliminar("");                              // lanza excepción → after throwing
        reg.registrar("", "sinCuenta", -5);           // before lo rechaza
    }
}
args() vincula los 3 parámetros a variables. after() throwing centraliza el log de errores de todos los métodos.
ValidacionAspect.aj
public aspect ValidacionAspect {

    // args() vincula los parámetros del método a variables del advice
    pointcut registrando(String nombre, String email, int edad) :
        execution(void RegistroUsuarios.registrar(String, String, int))
        && args(nombre, email, edad);

    // before: valida los datos ANTES de que lleguen a registrar()
    before(String nombre, String email, int edad)
            : registrando(nombre, email, edad) {
        if (nombre.isEmpty())
            throw new IllegalArgumentException("Nombre vacío");
        if (!email.contains("@"))
            throw new IllegalArgumentException("Email inválido: " + email);
        if (edad < 0 || edad > 120)
            throw new IllegalArgumentException("Edad inválida: " + edad);
        System.out.println("  [OK] Validado: " + nombre);
    }

    // after throwing: centraliza el log de errores de TODOS los métodos
    after() throwing(Exception ex)
            : execution(* RegistroUsuarios.*(..)) {
        System.err.println("  [ERROR] "
            + thisJoinPoint.getSignature().getName()
            + " → " + ex.getMessage());
    }
}

⚡ Procesador de Tareas — around() y proceed()

around() es el único advice que puede decidir si el método original se ejecuta o no. proceed() delega al método real; si no se llama, el método no ejecuta. Aquí lo usamos para memoizar resultados costosos y evitar reprocesamiento.

Simula una tarea costosa (150 ms). El aspecto evita que se reprocese la misma tarea dos veces.
ProcesadorTareas.java
public class ProcesadorTareas {

    public String ejecutarTarea(String nombre) {
        System.out.println("  [CPU] Procesando: " + nombre + " (150ms...)");
        try { Thread.sleep(150); } catch (InterruptedException e) {}
        return "resultado-de-" + nombre;
    }

    public void invalidarTarea(String nombre) {
        System.out.println("  [CPU] Tarea invalidada: " + nombre);
    }

    public static void main(String[] args) {
        ProcesadorTareas proc = new ProcesadorTareas();
        System.out.println(proc.ejecutarTarea("reporteAnual")); // → CPU
        System.out.println(proc.ejecutarTarea("reporteAnual")); // → Caché
        System.out.println(proc.ejecutarTarea("reporteAnual")); // → Caché
        proc.invalidarTarea("reporteAnual");                    // limpia caché
        System.out.println(proc.ejecutarTarea("reporteAnual")); // → CPU de nuevo
    }
}
around() consulta el caché antes de llamar a proceed(). Si hay resultado, retorna directamente; el CPU no trabaja.
ResultadoCacheAspect.aj
import java.util.HashMap;
import java.util.Map;

public aspect ResultadoCacheAspect {

    private Map<String, String> cache = new HashMap<>();

    pointcut ejecutando(String nombre) :
        execution(String ProcesadorTareas.ejecutarTarea(String)) && args(nombre);

    pointcut invalidando(String nombre) :
        execution(void ProcesadorTareas.invalidarTarea(String)) && args(nombre);

    // around: sirve desde caché o ejecuta la tarea real
    String around(String nombre) : ejecutando(nombre) {
        if (cache.containsKey(nombre)) {
            System.out.println("  [CACHÉ] Resultado listo: " + nombre);
            return cache.get(nombre);   // NO llama proceed() → CPU no trabaja
        }
        String res = proceed(nombre);   // ejecuta la tarea real
        cache.put(nombre, res);
        System.out.println("  [CACHÉ] Resultado guardado: " + nombre);
        return res;
    }

    // after: limpia la entrada al invalidar la tarea
    after(String nombre) : invalidando(nombre) {
        if (cache.remove(nombre) != null)
            System.out.println("  [CACHÉ] Entrada eliminada: " + nombre);
    }
}

Library.java — lógica de negocio pura
public class Library {

    public void lendBook(Member member, Book book) {
        if (!book.isAvailable()) {
            System.out.println("El libro '" + book.getTitle() + "' no está disponible.");
            return;
        }
        book.setAvailable(false);
        member.addLoan(book.getIsbn());
        System.out.println(member.getName() + " tomó: " + book.getTitle());
    }

    public void returnBook(Member member, Book book) {
        book.setAvailable(true);
        member.removeLoan(book.getIsbn());
        System.out.println(member.getName() + " devolvió: " + book.getTitle());
    }
}

Aspecto 1 — Validación de deuda (before)

Intercepta lendBook() y rechaza el préstamo si el socio tiene deuda pendiente, sin que Library sepa nada de esta regla.

DebtCheckAspect.aj
public aspect DebtCheckAspect {

    pointcut lending(Member m, Book b) :
        execution(void Library.lendBook(Member, Book)) && args(m, b);

    before(Member m, Book b) : lending(m, b) {
        if (m.hasDebt()) {
            System.out.println("[DEUDA] " + m.getName()
                + " tiene deuda — préstamo bloqueado.");
            throw new IllegalStateException("El socio tiene deuda pendiente.");
        }
    }
}

Aspecto 2 — Límite de préstamos (around)

Usa around() para envolver lendBook() y controlar el flujo completo: solo llama a proceed() si el socio no superó el límite de 3 libros.

LoanLimitAspect.aj
public aspect LoanLimitAspect {

    private static final int MAX_LOANS = 3;

    pointcut lending(Member m, Book b) :
        execution(void Library.lendBook(Member, Book)) && args(m, b);

    // around: decide si ejecutar el préstamo o bloquearlo
    void around(Member m, Book b) : lending(m, b) {
        if (m.loanCount() >= MAX_LOANS) {
            System.out.println("[LIMITE] " + m.getName()
                + " ya tiene " + MAX_LOANS + " préstamos activos.");
            return; // NO llama proceed() → el método no se ejecuta
        }
        proceed(m, b); // ejecuta Library.lendBook normalmente
    }
}

Aspecto 3 — Registro de actividad (after returning)

Se ejecuta solo cuando el préstamo o la devolución terminan con éxito, capturando ambas operaciones en un log.

ActivityLogAspect.aj
public aspect ActivityLogAspect {

    // Captura lendBook Y returnBook
    pointcut libraryOps(Member m, Book b) :
        (execution(void Library.lendBook(Member, Book))
         || execution(void Library.returnBook(Member, Book)))
        && args(m, b);

    // Solo si la operación completó sin excepción
    after(Member m, Book b) returning : libraryOps(m, b) {
        String op = thisJoinPoint.getSignature().getName()
                        .equals("lendBook") ? "PRESTAMO" : "DEVOLUCION";
        System.out.println("[LOG] " + op + " | Socio: " + m.getId()
            + " | ISBN: " + b.getIsbn()
            + " | Prestamos activos: " + m.loanCount());
    }
}

Un sistema de notas universitario donde los aspectos validan el rango de la calificación (0.0–5.0) antes de guardarla y notifican automáticamente cuando un estudiante queda en riesgo de pérdida, todo sin que GradeBook maneje esa lógica.

public class Student {

    private String name;

        this.code = code;
        this.name = name;
    }

    public String getName() { return name; }

public class GradeBook {
    // Registra la nota de un estudiante en una materia
    public void recordGrade(Student student, String subject, double grade) {
        System.out.printf("Nota registrada: %s | %s | %.1f%n",
            student.getName(), subject, grade);

Aspecto 1 — Validación de rango (before + args)

Usa args() para capturar los parámetros del método y rechazar la nota antes de que llegue a GradeBook.

GradeValidationAspect.aj
public aspect GradeValidationAspect {

    pointcut gradeRecording(Student s, String subject, double grade) :
        execution(void GradeBook.recordGrade(Student, String, double))
        && args(s, subject, grade);

    before(Student s, String subject, double grade)
            : gradeRecording(s, subject, grade) {

        if (grade < 0.0 || grade > 5.0) {
            throw new IllegalArgumentException(
                "Nota inválida para " + s.getName()
                + " en " + subject + ": " + grade
                + " (debe estar entre 0.0 y 5.0)");
        }
    }
}

Aspecto 2 — Alerta de riesgo académico (after returning)

Intercepta computeAverage() y captura el valor de retorno. Si el promedio está por debajo de 3.0, dispara una alerta automática.

AcademicRiskAspect.aj
public aspect AcademicRiskAspect {

    pointcut averageCalc(Student s) :
        execution(double GradeBook.computeAverage(Student, java.util.List))
        && args(s, *);

    // Captura el double retornado por computeAverage
    after(Student s) returning(double avg) : averageCalc(s) {
        System.out.printf("[PROMEDIO] %s → %.2f%n", s.getName(), avg);
        if (avg < 3.0) {
            System.out.println("[ALERTA] " + s.getName()
                + " está en riesgo académico. Promedio: " + avg);
            // Aquí se podría enviar un email, notificación push, etc.
        }
    }
}

Uno de los usos más potentes de around(): interceptar consultas costosas y servir resultados desde caché sin que el servicio de negocio cambie una sola línea. Un segundo aspecto invalida la caché automáticamente cuando los datos cambian.

Clase de negocio — servicio con consultas "lentas"

ProductCatalog.java
import java.util.*;

public class ProductCatalog {
    private Map<String, Double> prices = new HashMap<>();

    public ProductCatalog() {
        prices.put("laptop",  1500.0);
        prices.put("mouse",     25.0);
        prices.put("keyboard",  75.0);
    }

    // Consulta "costosa" (simula acceso a BD)
    public double getPrice(String productId) {
        System.out.println("  [DB] Consultando precio de: " + productId);
        try { Thread.sleep(200); } catch (InterruptedException ignored) {}
        return prices.getOrDefault(productId, -1.0);
    }

    // Actualización — debe invalidar la caché del producto
    public void updatePrice(String productId, double newPrice) {
        prices.put(productId, newPrice);
        System.out.println("  [DB] Precio actualizado: " + productId
            + " → " + newPrice);
    }
}

Aspecto 1 — Caché con around()

El advice around() revisa si el resultado ya está en caché antes de llamar a proceed(). Si lo está, retorna directamente sin tocar la base de datos.

CacheAspect.aj
import java.util.HashMap;
import java.util.Map;

public aspect CacheAspect {

    // Mapa interno: productId → precio cacheado
    private Map<String, Double> cache = new HashMap<>();

    pointcut priceQuery(String productId) :
        execution(double ProductCatalog.getPrice(String)) && args(productId);

    pointcut priceUpdate(String productId) :
        execution(void ProductCatalog.updatePrice(String, double))
        && args(productId, *);

    // around: intercepta getPrice y sirve desde caché si está disponible
    double around(String productId) : priceQuery(productId) {
        if (cache.containsKey(productId)) {
            System.out.println("  [CACHE HIT] " + productId
                + " → " + cache.get(productId));
            return cache.get(productId); // NO llama proceed()
        }
        // Cache miss: ejecuta la consulta real
        double result = proceed(productId);
        cache.put(productId, result);    // guarda en caché
        System.out.println("  [CACHE SET] " + productId + " = " + result);
        return result;
    }

    // Invalida la entrada de caché cuando el precio cambia
    after(String productId) : priceUpdate(productId) {
        if (cache.remove(productId) != null) {
            System.out.println("  [CACHE EVICT] " + productId);
        }
    }
}

AspectJ vs Spring AOP

Ambos implementan AOP en Java, pero con diferencias importantes. AspectJ es más poderoso; Spring AOP es más sencillo de configurar.

Característica AspectJ (compile-time) Spring AOP
Tipos de Join Points Métodos, constructores, campos, excepciones, inicialización Solo métodos públicos
Clases interceptables Cualquier clase Java Solo beans de Spring
Performance ✓ Mejor (sin overhead en runtime) ~ Pequeño overhead por proxy
Configuración Requiere plugin Maven/Gradle ✓ Automática con Spring Boot
Weaving Compile-time, Load-time Runtime (proxies dinámicos)
Inter-type declarations ✓ Sí (agregar campos/métodos) ✗ No
declare parents ✓ Sí ✗ No
Curva de aprendizaje Mayor ✓ Menor
Casos de uso Máximo control, sin Spring, sistemas legados Apps Spring típicas de producción
En el mundo real: Spring usa AspectJ internamente. @Transactional, @Cacheable, @Secured y @Async son todos aspectos bajo el capó.

¿Cuándo usar AOP?

AOP no es una bala de plata. Úsalo cuando el beneficio de separación supera la complejidad añadida.

✓ Úsalo para...

  • Logging y trazabilidad de métodos
  • Medición de performance / métricas
  • Autenticación y autorización centralizada
  • Manejo de transacciones de base de datos
  • Auditoría y registro de actividad
  • Retry automático con backoff
  • Caché de resultados de métodos
  • Validación de parámetros de entrada

✗ No lo uses para...

  • Lógica de negocio principal del dominio
  • Proyectos pequeños o scripts simples
  • Cuando el equipo no conoce AOP
  • Cuando la "magia" dificulta el debugging
  • Reemplazar inyección de dependencias
  • Lógica que varía por cada clase individualmente
// Resumen Final

Lo que aprendimos

El problema que resuelve AOP

Los cross-cutting concerns (logging, seguridad, transacciones) se repiten en decenas de clases con OOP puro, violando DRY y SRP. AOP externaliza ese código a Aspectos.

Los 6 conceptos esenciales

Aspect → módulo del concern. Join Point → dónde puede actuar. Advice → qué hace. Weaving → cómo se combina. Inter-Type Declaration → modifica la estructura en compilación. Pointcut → dónde QUIERO que actúe.

OOP y AOP: Complementarios

OOP modela el dominio (clases, herencia, polimorfismo). AOP maneja la infraestructura transversal. Los dos paradigmas trabajan juntos en cualquier aplicación real.

AspectJ en producción

Spring Framework usa AOP internamente para @Transactional, @Cacheable, @Secured. Hibernate usa AOP para lazy loading. Mockito usa proxies AOP.

"AOP no es una bala de plata, pero es una herramienta poderosa en el arsenal del desarrollador. El secreto está en usarla con juicio: cuando el código de negocio empieza a llenarse de lógica de infraestructura repetida, ese es el momento de crear un Aspecto."
